Query 的生命週期：staleTime 與 gcTime

這是你曾說「熟悉基本用法，但快取機制不熟」的第一塊拼圖——搞懂一個 query 從「新鮮」到「被清掉」中間到底發生了什麼事。

這堂課結束後你能做到 分辨 staleTime 和 gcTime 各自控制的是哪一段時間，並能準確預測：「切換分頁再切回來，會不會重新打 API？」

一個 query 的四個階段

React Query 的快取資料不是「有」或「沒有」這麼簡單，而是會經過幾個明確的階段：

fresh（新鮮） → stale（過期） → inactive（無人訂閱） → 從快取移除

每個轉換點都由一個獨立的設定控制，這正是最容易搞混的地方：

staleTime — 控制 fresh → stale

資料在 fresh 狀態時，React Query 完全不會重新打 API——即使你切換分頁再切回來、或視窗重新取得焦點，都只會直接吃快取。 只有當資料變成 stale，這些「背景重新抓取」的時機才會被觸發。

staleTime 的預設值是 0——也就是說，資料一拿到手就立刻是 stale。這也是為什麼很多人會覺得「React Query 怎麼一直在背景打 API」，其實不是 bug，是預設行為。

gcTime — 控制 inactive → 從快取移除

當某個 query 已經沒有任何 component 在用它（例如你切換到別的頁面），它會先進入 inactive 狀態，但資料還留在快取裡，沒有立刻消失。 gcTime（v4 之前叫 cacheTime）決定這個 inactive 的資料要在快取裡留多久，預設是 5 分鐘。

TkDodo 在原文中提到：「I have rarely ever needed to tamper with the gcTime」——換句話說，這個設定幾乎不太需要動，反而是 staleTime 才是你會常常想調整的那個。

為什麼容易搞混

這兩個設定管的是完全不同的兩段時間：staleTime 管「資料還算不算新鮮」，決定要不要背景重打 API；gcTime 管「沒人要用的資料還能不能從快取直接拿到」，決定要不要整個丟掉重新 loading。 把兩者混在一起想，就會出現「明明設了 staleTime: 5000，怎麼過一段時間再回來還是 loading」這種困惑——那通常其實是撞到了 gcTime 把資料整個清掉了。

情境：你把 staleTime 設成 1 分鐘。使用者打開頁面看到資料，切到別的 tab 待了 30 秒，切回來。這時會發生什麼？
